Сноски:
*1  OpenHands: ядро MIT, но каталог enterprise/ под отдельной коммерческой лицензией.
*2  Расширения VS Code/JetBrains: код локально, но модель обычно облачная (DeepSeek
    API). "Self-hosted" в полном смысле дают только Hermes и OpenHands.
*3  Hermes подключает DeepSeek как OpenAI-compatible endpoint; отдельной "кнопки
    DeepSeek" в доках нет.
*4  Aider: можно задать основную и weak/editor-модель, но не полноценные роли как у IDE.
*5  Continue: vision зависит от выбранной модели (мультимодальные провайдеры).
*6  Нативной Figma-интеграции нет ни у кого. Реальный путь - vision по скриншоту
    плюс сторонний MCP-сервер Figma (например Framelink/Figma MCP) у инструментов
    с MCP: Hermes, Cline, Roo Code, Continue, OpenHands. Aider без MCP - только
    скриншот/экспорт вручную.
*7  Aider: контроль через git - правки идут коммитами, легко смотреть/откатывать.
*8  OpenHands работает автономно в sandbox; diff виден в треё/логе, но модель
    "одобри каждое действие" слабее, чем у Cline.
*9  Continue: запуск команд есть в agent-режиме, но это не основной сценарий.
*10 Aider: есть web-UI режим, но не browser automation для preview макета.
*11 Aider: откат через git (checkout/reset), а не встроенные checkpoints.
*12 OpenHands: восстановление через сессии/траектории, не пофайловые снапшоты.
*13 Hermes: CLI + интеграции Telegram/Discord/Slack/WhatsApp; Linux/macOS/WSL2.
*14 Cline: VS Code, JetBrains, Cursor, Windsurf, Zed, Neovim, отдельный CLI.
*15 OpenHands: web (Agent Canvas), CLI, SDK; self-host через Docker.
*16 Hermes: мощный набор фич, но требует серверного setup, проверки безопасности
    и подтверждения аутентичности источника (.ru vs nousresearch.com).
*17 OpenHands: самый тяжёлый setup (Docker/sandbox), для ежедневной frontend-
    работы может быть избыточен.

3. ЗА / ПРОТИВ (кратко)
================================================================================

Hermes Agent (автономный, self-hosted)
  + Полный агентный цикл: терминал, файлы, браузер, vision, память, субагенты.
  + MCP, checkpoints/rollback - сильно для recovery после ошибок.
  + Полный self-hosted и нулевая телеметрия - максимум контроля.
  - Серверный setup, безопасность, зрелость UX - тяжелее IDE-расширений.
  - Нужно подтвердить аутентичность (.ru-зеркало vs официальный Nous-источник).
  - Для daily IDE-работы избыточен.

Aider (CLI)
  + Самый аккуратный repo-first workflow: правки = git-коммиты, лёгкий ревью/откат.
  + Прямая поддержка DeepSeek, vision, авто-fix lint/test, repo map.
  + Минимум "магии", предсказуемые точечные правки.
  - CLI-first: дизайнеру/PM менее удобно.
  - Нет MCP -> Figma только через ручной экспорт/скриншот.
  - Нет browser-preview макета.

Cline (IDE-агент)
  + Полный end-to-end цикл в IDE: файлы, терминал, браузер, vision.
  + Каждое действие требует подтверждения - хороший контроль diff.
  + MCP + checkpoints; работает во многих редакторах и как CLI.
  - При автономной работе дороже по токенам.
  - Без дисциплины в промптах может делать широкий рефактор.

Roo Code (IDE-агент) - НЕ РЕКОМЕНДУЕТСЯ
  + Богатый набор (режимы, per-mode модели, MCP, checkpoints, browser).
  - Репозиторий ARCHIVED с 2026-05-15: развитие остановлено, поддержки нет.
  - Брать в пилот рискованно; рассматривать только как форк/исторический референс.

Continue (copilot)
  + Лучший повседневный помощник: chat/edit/autocomplete, роли моделей.
  + Гибкая конфигурация провайдеров, удобно посадить DeepSeek как daily-модель.
  + VS Code + JetBrains.
  - Не полноценный автономный агент для крупных Figma-to-prototype задач.
  - Vision и agent-команды зависят от модели/режима, не основной сценарий.

OpenHands (автономный)
  + Настоящий "developer agent": план, правки, команды, браузер, vision, MCP.
  + Self-hosted, MIT (ядро); хорош для сложных автономных задач.
  - Самый большой setup overhead (Docker/sandbox), безопасность, стоимость.
  - Для ежедневного frontend-прототипа избыточен; контроль правок слабее Cline.

7. ПРОВЕРКА ПОДКЛЮЧЕНИЯ DeepSeek (для этапа пилота)
================================================================================
1. Зафиксировать, какой DeepSeek доступен: официальный DeepSeek API, OpenRouter,
   Together/Fireworks или локальный endpoint.
2. Создать именно developer API key (подписка chat/app != API key).
3. Endpoint: base URL (https://api.deepseek.com), model id (deepseek-chat /
   deepseek-reasoner), формат auth header, совместимость с OpenAI Chat Completions.
4. Smoke test вне инструмента: запрос "return only OK", сохранить ответ в лог.
5. Подключить endpoint в один инструмент, прочитать один файл -> мелкая правка.
6. Только после этого - полноценный Figma-to-prototype сценарий.

Типовые причины ошибок:
  - используется подписка chat/app, а не API key;
  - неверный model id;
  - ожидается OpenAI-compatible endpoint, указан не тот base URL;
  - key не в той переменной окружения;
  - нужен routing через OpenRouter/LiteLLM;
  - network/proxy/firewall;
  - модель умеет chat, но не tool use/function calling в нужном формате.

================================================================================
8. ЕДИНЫЙ PROMPT ДЛЯ СРАВНЕНИЯ
================================================================================
Ты работаешь в существующем frontend repo. Нужно реализовать экран по Figma input.
Сначала изучи структуру проекта и существующие компоненты. Не переписывай
архитектуру. Сохраняй изменения минимальными. Перед правками перечисли файлы,
которые планируешь менять. После правок запусти доступную проверку build/lint/test.
Если проверка падает, исправь причину и повтори. В финале дай список изменённых
файлов, результат проверок и известные ограничения.

================================================================================
9. КРИТЕРИЙ УСПЕХА
================================================================================
1. Инструмент подключается к DeepSeek без ручных обходов.
2. Setup воспроизводится по инструкции за 15-30 минут.
3. Один Figma-derived экран собирается за приемлемое время.
4. Изменения проходят build.
5. Diff ревьюится без ощущения, что проект переписан.
6. После ошибки можно продолжить с последней успешной точки.
