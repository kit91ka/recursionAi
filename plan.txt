0. КРАТКОЕ РЕЗЮМЕ
--------------------------------------------------------------------------------
Нужно сделать SPA на Angular с авторизацией по JWT и справочником категорий
(CRUD): список с поиском/сортировкой/бесконечной прокруткой, добавление,
просмотр/редактирование, удаление с подтверждением.

Стек (обоснование ниже):
  - Angular (latest stable, standalone, signals) — поднимать через `npx @angular/cli`.
  - PrimeNG + PrimeIcons — макет нарисован под PrimeNG (слои datatable/input/
    overlay/dialog). Тема настраивается под токены Figma.
  - OpenAPI-генератор клиента из Swagger backend (требование ТЗ).
  - Управление состоянием — сервисы на signals (без NgRx, объём не требует).

Backend:
  - Base URL: https://zidium3-backend.zidium.net/
  - OpenAPI (Front): https://zidium3-backend.zidium.net/swagger/front/swagger.json
  - Тестовый пользователь: test / 77777

1. РАСХОЖДЕНИЯ ТЗ ↔ МАКЕТ ↔ API (важно согласовать до старта)
--------------------------------------------------------------------------------
1.1 Поля справочника.
    - ТЗ: для /categories поля «Id» и «Name».
    - Макет: колонки «Name» и «Description» (+ Description в модалках).
    - API CategoryDto = { id:int, name:string } — поля Description НЕТ.
    => РЕШЕНИЕ: следуем ТЗ + API. Колонки: Id, Name. Поле Description НЕ реализуем
       (макет обобщённый — «у каждого справочника свои поля», прямо сказано в ТЗ).
       В модалке Add/Edit: Id (текст, readonly, только в Edit) + Name (input).

1.2 Колонка Id в списке.
    - ТЗ перечисляет поля «Id» и «Name». Макет Id-колонку не показывает.
    => РЕШЕНИЕ: показываем обе колонки (Id, Name) по ТЗ. Сортировка — по Name
       (в API только sortDesc, без выбора поля — значит сортировка идёт по Name).

1.3 Редактирование: страница vs модалка.
    - ТЗ: «Url в браузере: /categories/{id}» (отдельный маршрут).
    - Макет: модальное окно поверх списка.
    => РЕШЕНИЕ: маршрутизируемая модалка — отдельный route /categories/:id и
       /categories/new, который открывает PrimeNG Dialog поверх списка. Так
       выполняется требование ТЗ к URL и сохраняется вид макета. Реализуется
       через дочерние маршруты с отдельным <router-outlet> или через резолв id
       в самом списке.

1.4 Тексты ошибок входа.
    - Макет показывает «User is blocked» (частный случай) и «Field is required».
    => РЕШЕНИЕ: «Field is required» — клиентская валидация required. Текст ошибки
       входа берём из ответа API (message), если его нет — дефолт. Не хардкодим
       «User is blocked» как единственный вариант.

1.5 pageSize.
    - В ТЗ размер страницы явно не задан, в API есть параметр pageSize.
    => РЕШЕНИЕ: ввести константу PAGE_SIZE (например 50). Грузить, пока
       items.length === pageSize. Согласовать значение при ревью.

      - сгенерированные сервисы: LogonService, CategoriesService (имена уточнить после генерации);
      - DTO: LogonRequestDto, LogonResponseDto, TokensResponseDto, RefreshTokenRequestDto,

4.5 Папку core/api пометить как генерируемую (не править вручную; при изменении API — regen).

5. КОНТРАКТЫ API (точно из swagger_front.json)
--------------------------------------------------------------------------------
Авторизация:
  POST /front/logon
       body LogonRequestDto { login, password }
       200  LogonResponseDto { token, refreshToken, user: { displayName, timezoneOffset } }
  POST /front/logon/refresh-token
       body RefreshTokenRequestDto { refreshToken }
       200  TokensResponseDto { token, refreshToken }
  GET  /front/logon/current-user -> CurrentUserDto  (для шапки/проверки сессии)

Все методы ниже требуют заголовок Authorization: Bearer <token>.

Категории:
  GET    /front/categories?search=&pageSize=&pageNumber=&sortDesc=
         200 CategoryListDto { items: CategoryDto[], canEdit: bool }
         (pageNumber начинается с 0; total в ответе НЕТ — пагинация по длине items)
  GET    /front/categories/{id} -> CategoryDto { id, name }
  POST   /front/categories            body EditCategoryDto { name }  -> 200 int (новый id)
  POST   /front/categories/{id}       body EditCategoryDto { name }  -> 200 (void)
  DELETE /front/categories/{id}       -> 200 (void)
  GET    /front/categories/name-exists?id=&name=  -> bool
         (id = текущая запись или null/пусто при добавлении; true => имя занято => невалидно)

7. АВТОРИЗАЦИЯ (JWT) — детально
--------------------------------------------------------------------------------
7.1 TokenStorage: хранит token, refreshToken в localStorage; экспонирует signal
    token() для реактивности; clear() при logout.
7.2 AuthService:
      - logon(login, password): POST /front/logon -> сохранить токены и user;
        вернуть Observable/Promise; ошибки прокинуть для показа в форме.
      - refresh(): POST /front/logon/refresh-token c refreshToken -> обновить токены;
        при провале -> logout() + redirect /login.
      - logout(): очистить storage, redirect /login.
      - currentUser: signal<CurrentUserDto | null>.
      - isAuthenticated: computed по наличию token.
7.3 authInterceptor (HttpInterceptorFn):
      - добавляет Authorization: Bearer <token> ко всем запросам к backend
        (кроме /front/logon и /front/logon/refresh-token);
      - на 401: запустить refresh (с защитой от параллельных рефрешей —
        общий inFlight$ / шаринг), затем повторить исходный запрос с новым токеном;
      - если refresh упал -> logout.
7.4 authGuard (CanMatchFn): isAuthenticated ? true : router.parseUrl('/login').
7.5 Безопасность:
      - токены не логировать;
      - Figma-токен из environment.ts НЕ тащить во фронтовый бандл прода
        (он использовался только на этапе анализа макета).

9. ЭКРАН СПИСКА (/categories) — макет «Справочник»
--------------------------------------------------------------------------------
Заголовок «Categories» (18/500). Справа сверху — кнопка «+ Add»
(иконка plus + текст), видна только при canEdit=true. Под заголовком — строка
поиска «Search» (PrimeNG IconField + InputText с иконкой лупы). Ниже — таблица
(PrimeNG Table) с колонками:
   - Id  (по ТЗ)
   - Name (кликабельный заголовок -> переключение sortDesc)
   - [действие] иконка-корзина в строке (видна только при canEdit) -> удаление
Строка кликабельна -> переход на /categories/:id (просмотр/редактирование).

9.1 Бесконечная прокрутка (по ТЗ):
   - Грузим страницы pageNumber=0,1,2… с PAGE_SIZE.
   - Запрашиваем следующую, пока вернувшееся число строк === PAGE_SIZE
     («или если ещё осталось место на странице» — догрузка, если контент
     не заполнил вьюпорт). Когда вернулось меньше PAGE_SIZE — hasMore=false.
   - Реализация: PrimeNG Table virtualScroll/lazy ИЛИ IntersectionObserver на
     «сентинел» в конце списка. Предпочтительно IntersectionObserver — точно под
     требование «догружать пока есть место».
   - Защита от гонок: не стартовать новый запрос, пока идёт текущий (loading).

9.2 Поиск:
   - Поле search -> debounce (~300 мс) -> сброс пагинации (pageNumber=0, items=[])
     -> перезагрузка с параметром search.
   - Использовать signal + toSignal/effect или RxJS debounceTime на valueChanges.

9.3 Сортировка:
   - Клик по заголовку «Name» -> инверсия sortDesc (изначально false)
     -> сброс пагинации -> перезагрузка. Индикатор направления в заголовке.

9.4 canEdit=false:
   - Скрыть «+ Add», иконки удаления, кнопку Save в модалке (всё редактирование).
   - Просмотр записи остаётся доступным (поля readonly).

9.5 Состояния: загрузка (skeleton/spinner), пусто («ничего не найдено»),
    ошибка загрузки (сообщение + повтор).

9.6 categories.store.ts (signal-стор):
    state: { items, canEdit, search, sortDesc, pageNumber, loading, hasMore, error }
    методы: loadNextPage(), reload() (сброс+первая страница),
            setSearch(v), toggleSort(), removeFromList(id), upsert(item).

10. ДОБАВЛЕНИЕ / РЕДАКТИРОВАНИЕ (модалка) — макеты «Add» / «Edit»
--------------------------------------------------------------------------------
Одна маршрутизируемая модалка CategoryEditDialog на два режима:
  - /categories/new  -> режим Add  (заголовок «Add»),  Id скрыт.
  - /categories/:id  -> режим Edit (заголовок «Edit»), Id показан как текст (readonly).
Вид (PrimeNG Dialog поверх затемнения):
  - Заголовок + крестик закрытия (X).
  - Поле «Id» (только Edit): текст, НЕ input (по ТЗ).
  - Поле «Name»: InputText.
  - Кнопки: «Close» (нейтральная #f4f4f5) и «Save» (синяя #005baa).
Поведение:
  - Edit: при открытии GET /front/categories/{id} -> заполнить форму.
  - Форма: name (required + асинхронная валидация name-exists).
  - Save:
      Add  -> POST /front/categories { name } -> получить новый id ->
              обновить список (upsert) -> закрыть модалку (навигация /categories).
      Edit -> POST /front/categories/{id} { name } -> обновить список -> закрыть.
  - Close / крестик / клик по затемнению -> навигация назад на /categories.
  - Save заблокирована, пока форма невалидна или идёт сохранение/валидация.
  - canEdit=false (для записи): все поля readonly, кнопка Save скрыта,
    остаётся только Close (режим просмотра).

10.1 Асинхронная валидация Name (по ТЗ):
   - AsyncValidator nameExistsValidator(currentId | null):
       GET /front/categories/name-exists?id={id|пусто}&name={value}
       true  -> ошибка { nameTaken: true } («название уже занято»);
       false -> валидно.
   - Дебаунс перед запросом (~300-400 мс), отмена предыдущего запроса
     (switchMap), индикатор «проверка…».
   - id = id текущей записи (Edit) или null/пусто (Add).
   - Пустое имя сначала отсекается required (валидатор name-exists не дёргаем).
